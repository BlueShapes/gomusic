gomusic / musicord のGo移植

最終更新: 2026-11-03 ・ 対象: github.com/blueshapes/gomusic（M1〜M4 実装済み、Docker は未着手）

概要 動作要件 起動 設定 コマンド 内部仕様 ログ 実測値 制限・未実装 デプロイ 開発用CLI

概要

Discord のボイスチャンネルで音楽を流すボット。元実装（Kotlin + Kord + Lavalink/LavaSrc）を Go（disgo）で書き直したもので、Lavalink を使わず yt-dlp 一本で音源を取得する。 

Discord slash command
  → disgo handler（goroutineで実行）
    → player.Manager（ギルドごとに1つの Player）
      → audio.Cache（yt-dlp | ffmpeg → cache/<videoID>.ogg）
      → audio.Reader（ogg パケット = 20ms フレーム）
        → voice.Conn（DAVE/E2EE で暗号化して送出）

設計の柱

  • パススルー: YouTube の bestaudio は 48kHz ステレオ opus / 20ms フレーム。 そのまま ogg に詰め替えるだけで送れる（音声処理ゼロ）
  • 100%再生は無変換: 音量100%ではデコードもしない
  • シークは読み飛ばし: パケットを先頭から捨てるだけ（実測 30秒位置へ 2ms）
  • DAVE(E2EE) 必須: 2026年以降のDiscord要件。dave-go（純Go）を使用

やらないこと

  • Lavalink / LavaSrc / 外部音声サーバ（不要）
  • ffmpeg による通常再生時の再エンコード（パススルー優先）
  • ライブ配信の再生（キャッシュが確定しないため拒否）
  • 音源のストリーミング開始（DL完了後に再生を開始する）

起動

cd ~/blueshapes/gomusic
go build -o musicord .

./musicord          # config.toml が無ければ既定値を書き出して終了する
$EDITOR config.toml # discord.token と discord.guild_ids を設定
./musicord          # 起動（スラッシュコマンドは起動時にギルドへ同期される）

初回起動では config.toml を生成して終了する（トークン未設定のまま起動しないため）。 設定ファイルに無いキーは既定値で補完されるので、項目を追加した後も古い設定ファイルをそのまま使える。

設定リファレンス（config.toml）

[discord]
token = "token is here"          # Bot トークン（必須）
guild_ids = []                   # コマンドを登録するギルドID（必須・1つ以上）

[yt_dlp]
bin = "yt-dlp"                   # 実行ファイル名 or パス
cookies = ""                     # 任意: cookies.txt（年齢制限/ボット判定対策）

extra_args = ["--no-js-runtimes", "--js-runtimes", "node"]

[audio]

cache_dir = "cache"              # ogg キャッシュの置き場
max_cache_mb = 4096              # キャッシュの総量上限（超過分は古い順に削除）
concurrency = 2                  # 同時に走る yt-dlp/ffmpeg の本数
キー既定意味
discord.token—未設定（"token is here"）だと起動を拒否する
discord.guild_ids—空だと起動を拒否する。グローバルコマンドではなくギルドコマンドとして登録
yt_dlp.cookies""指定時のみ --cookies を付与
yt_dlp.max_playlist100--playlist-end として渡す。上限を超える分は取得すらしない（解決は約4ms/件）
yt_dlp.extra_args--no-js-runtimes --js-runtimes node全 yt-dlp 呼び出しに前置される。順序が重要（先に --no-js-runtimes）

audio.concurrency2セマフォ本数。3本目以降は待機

内部仕様

1. メタデータ解決（yt-dlp）

入力コマンド実測
検索語yt-dlp -J --flat-playlist --no-warnings --playlist-end N "ytsearchN:query"5件で約1.8s、100件で約2.5s
URL（動画/プレイリスト）yt-dlp -J --no-playlist --flat-playlist --no-warnings URLプレイリスト123件で約2.6s

--flat-playlist を使うのは、完全展開が約5倍遅いため（5件で8.6s vs 1.8s）。 その代償として is_live が取れないので、ライブ判定はダウンロード時に回している。 動画+リストのURL（&list=RD...）は --no-playlist により単曲扱い。

2. キャッシュ生成（audio.Cache.Prepare）

yt-dlp -f "bestaudio[ext=webm]/bestaudio/best" \
       --match-filter "!is_live" --no-playlist --playlist-items 1 -o - URL
  | ffmpeg -i pipe:0 -vn -map 0:a -c:a copy -f ogg cache/<id>.ogg.part
  → 先頭5パケットを検証（20ms かつ 1275バイト以下）
  → 不合格なら -c:a libopus -b:a 96k -ar 48000 -ac 2 -frame_duration 20 で作り直す
  → os.Rename(.part → .ogg) で確定（原子的）
  • パススルー優先: 再エンコードは「詰め替えで済まないソース」だけ。完了ログに mode=passthrough / mode=re-encoded が出る
  • 合流: 同じ videoID への同時要求は1ジョブを共有（inflight マップ）
  • 同時実行: audio.concurrency 本のセマフォ
  • タイムアウト: 1曲10分。超過時は yt-dlp timed out
  • キャッシュヒット: os.Stat のみ＋mtime 更新（LRU用）。ダウンロードしない
  • 削除: 生成完了のたびに総量を確認し、max_cache_mb を超えていれば mtime 昇順に削除
  • ライブ拒否: --match-filter "!is_live"。ライブはファイルが完成しないため

3. ダウンロードが走るタイミング

契機内容
/play 直後（非同期）その呼び出しで渡された先頭3曲を go prefetch()。キューの位置ではなく「呼び出し単位」である点に注意
曲の切り替え時advance() が次の曲を Prepare。未キャッシュならここでDL（その間は無音）
その他のコマンド一切ダウンロードしない（/seek も不可。既存ファイルの読み直しのみ）

4. 再生（player.provider）

  • disgo の OpusFrameProvider を実装。呼ばれるたびに ogg から1パケット（20ms）を返す
  • 一時停止＝フレームを返さない（nil, nil）。disgo が無音5フレーム→SpeakingFlagNone まで面倒を見るので、位置も自然に停止する
  • 曲終了＝ogg の EOF。別goroutineで onEnd を呼び、次曲へ（SetOpusFrameProvider が旧providerを Close するため、同期実行だと自己デッドロックする）
  • 再生位置＝読み出したパケットの20ms累積（フレーム数×20ms）
  • ループ（queue）は終了した曲をキュー末尾へ再追加してから次へ

5. シーク

ファイルを先頭から読み直し、目標位置までパケットを捨てる方式。granule 索引は持たない。 実測 30秒位置へ 2ms、10分の曲でも約50ms（読み出しは 0.83ms/10秒）。

6. 音量

設定処理コスト
100%完全パススルー（デコードしない）ゼロ
0〜200%pion/opus でデコード → ゲイン＋リミッター → kazzmir/opus-go でエンコード（128kbps）約410µs/フレーム ≒ 1ギルドあたり1コアの約2%

100%超はハードクリップせず、-3dBFS から tanh で丸める（実測: 150%で原本ピーク85.7%の音源をハードクリップすると0.007%のサンプルが張り付く）。 音量変更は次フレームから反映され、ストリームの再起動やギャップは発生しない。音量はメモリ保持（再起動で100%に戻る）。

7. キューとギルド状態

  • ギルドごとに player.Player（Manager が map で保持）。永続化はしない
  • queue は「待機中の曲」のみ。current は別フィールド
  • すべての状態変更は sync.Mutex 保護。DL・接続は advance() のgoroutineで行う

8. 自動退出

  • GuildVoiceLeave: 抜けた人がボットと同じVCの最後の人間なら切断＋Player破棄（判定は Member.User.Bot でボットを除外、自分自身も除外）
  • GuildVoiceStateUpdate: ボット自身が切断された（キック等）場合は voice conn と Player を掃除

9. DAVE（E2EE）と disgo の落とし穴

問題対策（実装済み）
DAVE 非対応だとVCに入れない（2026年以降の必須要件）voice.WithDaveSessionCreateFunc(session.CreateFunc())（dave-go、純Goなので cgo 不要）
disgo は既定で何もキャッシュしない（CacheFlags=0）ため Caches.VoiceState() が常に falsecache.WithCaches(FlagVoiceStates, FlagMembers) を明示
gatewayイベントは同期配送。ハンドラが conn.Open で待つと、待っているイベント自体が配送されず固まるr.Use(middleware.Go) でハンドラをgoroutine化
VC接続（DAVEハンドシェイク）は数秒かかり、interaction の3秒応答期限を超える/play /join は先に DeferCreateMessage → 結果はfollowup。接続自体は30秒の独自タイムアウト

デプロイ（Docker）

Dockerfile は2ステージ構成。ビルド側は CGO_ENABLED=0 の静的バイナリ （dave-go / pion-opus / kazzmir-opus-go はいずれも cgo 非依存）、実行側は node:24-bookworm-slim + ffmpeg + yt-dlp_linux。 

mkdir -p data                        # 先に作る（無いと root 所有で作られる）
docker compose build
docker compose run --rm gomusic      # 初回: data/config.toml を生成して終了
$EDITOR data/config.toml             # token と guild_ids を書く
docker compose up -d
docker compose logs -f

状態は全てホストの ./data に入る（data/config.toml と data/cache/）。 WORKDIR が /app なので、config.toml の相対パスも cache_dir = "cache" も自動的にこのディレクトリ配下に解決される（env 上書き不要）。

Linux で uid が 1000 でない場合は sudo chown -R 1000:1000 data が必要 （コンテナは node = uid 1000 で動く）。書き込み不可なら起動時に cache dir /app/cache is not writable で落ちる。Docker Desktop (macOS) は通常そのまま動く。

構成要素内容
ベースnode:24-bookworm-slim（LTS・maintenance、Debian 12 固定）
yt-dlp公式 PyInstaller バイナリ（yt-dlp_linux / yt-dlp_linux_aarch64）。 EJS スクリプト同梱なので python 不要。YTDLP_VERSION でピン留め
JS ランタイムベースイメージの node をそのまま使用（--js-runtimes node は既定の extra_args に設定済み）
ffmpegapt（libopus 入り）。ogg 詰め替えと再エンコードに使用
永続化./data:/app の単一バインド。data/config.toml と data/cache/ がホストに残る（名前付きボリュームは使わない）
実行ユーザnode（uid 1000）。/app はイメージ側で chown 済み（バインド時はホスト側の所有者に従う）
メモリmem_limit: 1536m（yt-dlp + node のピークが約430MB、concurrency=2 を見込む）
停止init: true + stop_grace_period: 20s（SIGTERM で終了、yt-dlp/ffmpeg の孤児を回収）

リリース手順

手順内容
1. 変更を貯めるRenovate のPRや通常のPRを main にマージ（fix: / feat: などの conventional commit）
2. リリースPRchore(main): release x.y.z が自動で作成・更新される（CHANGELOG とバージョン）
3. マージしてリリースそのPRをマージ → タグ vx.y.z が作られ image.yml が走る → ghcr.io/…:x.y.z / :x.y / :latest

初回はタグが無いため 1.0.0 が提案される（release-type: simple）。0.x から始めたい場合は release-please-config.json（manifest モード + initial-version）を追加するか、 事前に v0.0.0 タグを打っておく。/leave 等の実装変更は fix: でパッチ、機能追加は feat: でマイナー上がる。

タグは ブランチ名 / sha-xxxxxxx / リリースタグ（v0.1.0 → 0.1.0 / 0.1）。 latest はリリースタグのときだけ付く（＝latest は常に最新リリースを指す）。 main への通常の push ではイメージを作らないので、依存更新などはリリースPRをマージするまで配布されない。

項目内容

docker pull ghcr.io/blueshapes/gomusic:latest   # 公開設定にしていれば
docker compose pull && docker compose up -d

開発用CLI（cmd/audioprobe）

Discord を使わずに音声層だけ検証できる。

go run ./cmd/audioprobe -search "lofi hip hop" -limit 5
go run ./cmd/audioprobe -resolve "https://www.youtube.com/@LofiGirl/videos"
go run ./cmd/audioprobe -prepare "https://youtu.be/dQw4w9WgXcQ"   # DLしてキャッシュへ
go run ./cmd/audioprobe -play cache/dQw4w9WgXcQ.ogg -seek 1m30s -packets 20
フラグ内容
-searchytsearch で解決（DLなし）
-resolveURL（動画/プレイリスト）を解決（DLなし）
-prepare解決してキャッシュ生成まで実行
-play / -seek / -packetsキャッシュ済み ogg のパケット読み出し・シーク時間の計測
